# Amilu ER 模型｜實體與 PK/FK 初步草案

> 資料來源：`amilu_討論總結.md`（Part 2 功能總覽、Part 3 關鍵機制設計決策）、`flowChart項目整理.md`，以及 `Excalidraw/flowChart圖形放置區/` 底下全部模組一～五的 flowchart 文字內容（含委託申請引導式表單欄位、開通創作者商店欄位、終止合作結算欄位等）。
> 這份文件只做「文字敘述版」的實體盤點，尚未畫成真正的 ER 圖，也還沒定案，用來跟你先對一輪範圍與命名，確認沒問題後再進入畫圖／建 schema 階段。

---

## 一、盤點到的實體清單

### 1. User（帳號）

- 對應：模組一 註冊／登入流程、手機驗證流程。
- 候選 PK：`email`（flowchart 明確標註「email（當主鍵，不得重複）」）。
- 主要欄位：密碼 hash、使用者名稱（可重複）、是否已完成手機驗證、手機號碼、身份旗標（委託人／創作者，支援雙身份）。
- 備註：委託人是預設身份，創作者身份是否開通另外看 CreatorProfile 是否存在該筆資料即可判斷，不一定要在 User 上加欄位。

### 2. CreatorProfile（創作者接案設定 / 創作者身份資料）

- 對應：模組三 開通創作者商店流程、Amilu 燈狀態邏輯。
- 候選 PK：`creator_id`；候選 FK：`user_id` → User（1 對 1，一個帳號最多一份創作者身份）。
- 主要欄位：收款戶頭、委託規範（ToS 相關文字）、授權範圍（是否可商用）、訂金%（30% / 50% / 無需先支付，三選一）、分段方案偏好（單段／3段／5段）、Amilu 燈手動狀態（開放／暫停）、是否已通過創作者商店開通申請（開通條件：可委託項目至少 1 筆）。
- 備註：外部顯示的「開放中」是由「手動開放」＋「可委託項目數 ≥ 1」＋「已開通商店」三條件同時成立才顯示，這是「衍生欄位／查詢邏輯」，不建議存成獨立狀態欄位，避免跟來源資料不同步。

### 3. Work（作品集 / 一般圖文）

- 對應：模組三 創作者作品上架流程；不需開通創作者商店也能發。
- 候選 PK：`work_id`；候選 FK：`creator_id` → CreatorProfile（或直接 → User，因為作品集不要求已開通創作者商店）。
- 主要欄位：圖片、文字內容、作品類型分類（By Type）、風格分類（By Style）。
- 備註：作品類型與風格是 Part 1.2 定義的固定分類清單，若要正規化，需要額外的 `WorkCategory`／`WorkStyle` 分類表，Work 與分類表是多對多還是單選需要跟你確認（目前文字敘述是「選擇作品類型分類」「選擇風格分類」，看起來像單選各一個，但 Part 1.2 說「一件作品可從多維度被找到」，這點有點模糊，需要你確認）。

### 4. CommissionItem（可委託項目）

- 對應：模組三 開通創作者商店流程 Step3、創作者作品上架流程「可委託項目」路徑。
- 候選 PK：`item_id`（flowchart 內有明確標註「可委託項目ID」欄位）；候選 FK：`creator_id` → CreatorProfile。
- 主要欄位：圖片（1 張以上）、委託標題、說明、價格（或價格區間）、是否可商用（沿用 CreatorProfile 的授權範圍設定或本項目獨立設定，需確認）。
- 備註：開通創作者商店的硬性條件是「可委託項目不可為 0 筆」，這條規則之後可以用「查詢 CommissionItem 是否至少 1 筆」實作，不需要另外存布林值。

### 5. Tag（自訂標籤）

- 對應：模組三，Work／CommissionItem 都可以掛自訂標籤；標籤本身由創作者自訂新增。
- 候選 PK：`tag_id`；候選 FK：`creator_id` → CreatorProfile（標籤是否跨創作者共用，或每個創作者各自維護一份標籤清單，需要跟你確認）。
- 關聯：Work 與 Tag 為多對多（需要 `Work_Tag` 中介表）；CommissionItem 與 Tag 也是多對多（需要 `CommissionItem_Tag` 中介表）。

### 6. Order（委託案件 / 契約）

- 對應：模組四 委託申請至契約成立完整狀態流（核心狀態機）、委託申請引導式表單。
- 候選 PK：`order_id`；候選 FK：`commissioner_id` → User（甲方／委託人）、`creator_id` → CreatorProfile（乙方／創作者）、`item_id` → CommissionItem（本次委託對應的可委託項目）。
- 主要欄位（契約快照，成立後鎖定不可改）：
  - 表單填寫內容：畫布方向、自訂尺寸、年齡分級（全年齡／R-18）、規格說明（自由文字）、參考圖片、授權層級（個人／商業）、甲方輸入預算、預期交件日。
  - 分段方案與訂金%（唯讀複製自 CreatorProfile 當時的設定，鎖進快照，之後 CreatorProfile 若異動不影響已成立的 Order）。
  - 付款方式（全額／訂金）、工作起訖日期、各分段 deadline、委託報價金額（由創作者在確認時給出，這裡跟你在 flowChart項目整理.md 裡記錄的「金額鎖定時機矛盾」有關，見下方「待確認事項」）。
  - 狀態欄位：需求填寫中／待創作者確認／契約成立／第 N 階段製作中／已交付待確認／已完成／已取消（委託人送出前主動取消）／終止合作（雙輸或已撥款後結算）／惡意棄單（乙方或甲方）。
- 備註：這是全案「分支最複雜」的實體，狀態欄位建議用一個 `status` enum 或拆成獨立的 `OrderStage` 子實體處理各階段細節（見下一項），需要跟你確認要不要拆。

### 7. OrderStage（訂單分段紀錄）

- 對應：模組四 50/50 雙向確認機制、每階段 deadline 與惡意棄單判定。
- 候選 PK：`stage_id`；候選 FK：`order_id` → Order。
- 主要欄位：階段序號、deadline、乙方上傳的稿件（含浮水印預覽版、正式版）、甲方確認狀態（人工確認／auto-confirm／未確認）、確認時間戳、本階段是否已撥款、本階段金額（依 `總價 ÷ 階段數` 無條件捨去、餘數併入最後階段的公式計算或直接落地存值，需確認）。
- 備註：如果決定拆這個實體，Order 本身就不需要重複存「當前進行階段」這種欄位，改成查詢 OrderStage 即可；模組五模擬金流撥款流程 flowchart 裡有標註 Order 層級要存「當前進行階段」「最近一次確定日期」，這點如果拆了 OrderStage 會變成冗餘欄位，需要跟你確認要不要保留在 Order 上做查詢加速用的快取欄位。

### 8. Payment（模擬金流／託管紀錄）

- 對應：模組五 模擬金流撥款流程。
- 候選 PK：`payment_id`；候選 FK：`order_id` → Order。
- 主要欄位：金額、類型（託管入款／訂金撥款／尾款撥款／退款）、狀態（待託管／已託管／已撥款／已退款）、時間戳、6% 抽成計算後的實拿金額。
- 備註：模擬金流不串真實綠界，這張表純粹是狀態紀錄用途，不需要對接真實金流欄位（如交易序號、金流商 callback 等）。

### 9. ConsentLog（契約同意紀錄 / 舉證鏈）

- 對應：Part 3.3 ToS 定型化契約與舉證鏈；模組一「契約同意紀錄」MVP 項目。
- 候選 PK：`log_id`；候選 FK：`order_id` → Order、`user_id` → User（哪一方按下同意）。
- 主要欄位：同意時間戳、契約內容快照（或內容雜湊值 hash）。
- 備註：甲乙雙方各自按一次「我已閱讀並同意」，理論上一筆 Order 會有兩筆 ConsentLog（甲方一筆、乙方一筆）。

### 10. Message（合作區留言）

- 對應：模組四 合作區圖文留言區（取代即時聊天室，非即時）。
- 候選 PK：`message_id`；候選 FK：`order_id` → Order、`sender_id` → User。
- 主要欄位：留言內容（圖文）、時間戳。

### 11. Review（評價）

- 對應：模組五 最簡評價系統。
- 候選 PK：`review_id`；候選 FK：`order_id` → Order、`reviewer_id` → User、`reviewee_id` → User。
- 主要欄位：分數（不填視為 0，但判定為「無評論」，不計入評比樣本數，這條規則要在應用層或查詢邏輯處理，不建議直接把 0 分計入平均分）。
- 備註：不論結案方式（正常走完／auto-confirm／終止合作）都會開放互評，這點不影響 ER 結構，只影響「什麼時候允許新增 Review」的業務邏輯。

### 12. Notification（通知）

- 對應：模組五 通知中心。
- 候選 PK：`notification_id`；候選 FK：`user_id` → User。
- 主要欄位：分類（專案通知／系統公告／互動）、內容、是否已讀、時間戳、是否已透過 email 發送（逾時提醒、auto-confirm 結果這類要站內＋email 雙管道）。

## 二、目前沒有列成獨立實體、但你可能會想確認的部分

- **WorkCategory / WorkStyle（作品類型、風格的固定分類表）**：Part 1.2 有寫死的四大類型清單（角色立繪、插畫……等 10 項）與風格清單（10 項），這兩份是否要建成獨立的查找表（lookup table），還是直接存成 Work 上的 enum 欄位，需要你決定。
- **終止合作 / 惡意棄單**：目前我把這兩種結案方式都當成 Order（或 OrderStage）上的一種狀態值處理，沒有另外開 `TerminationRequest` 或 `AbandonmentRecord` 實體，因為 flowchart 裡的判斷邏輯（撥款前後、deadline+5天）都可以從 Order／OrderStage／Payment 現有欄位查詢推導出來。如果你希望保留「誰在什麼時間點發起終止申請」這種操作紀錄（而不只是最終結算結果），可能需要一張 `OrderEvent` 或 `TerminationRequest` 記錄表。

## 三、待確認事項（會影響 PK/FK 設計，需要你先決定）

1. **委託報價金額的鎖定時機還沒定案**：`flowChart項目整理.md` 與 `amilu_討論總結.md` 2026/9/20 修改紀錄都提到，「委託申請引導式表單」跟「委託申請至契約成立完整狀態流」在金額鎖定時機上互相矛盾——送出後是否經過議價聊天室、創作者確認同步報價、甲方再確認金額，這個三段式流程還沒定案。這會直接影響 Order 要不要拆出「報價/議價」子實體，還是金額欄位就落在 Order 本體上，建議這點先跟你們團隊定案後我再收斂 Order 的欄位設計。
2. **Work 與分類的多對多／單選**：見上方 Work 實體備註。
3. **Tag 是否跨創作者共用**：見上方 Tag 實體備註。
4. **OrderStage 要不要拆成獨立實體**：如果拆，Order 上部分欄位（當前階段、最近確認日期）會變成冗餘快取欄位；如果不拆，Order 就要用比較複雜的欄位或 JSON 結構存多階段資訊。
5. **CommissionItem 的「是否可商用」是否獨立於 CreatorProfile 的授權範圍設定**：flowchart 備註寫「若該可委託項目未開放商用（接案設定—授權範圍）」，讀起來像是共用 CreatorProfile 的設定而非各項目獨立設定，但也可能是我理解錯誤，需要你確認。
