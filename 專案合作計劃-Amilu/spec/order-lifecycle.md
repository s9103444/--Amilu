## 一、委託狀態機

### ORDER.status

| 狀態 | 進入條件 | 誰能讓它離開這個狀態 | 離開後去哪裡 | 對應畫面 |
| --- | --- | --- | --- | --- |
| 待乙方報價 | 甲方按「我要委託」送出申請（`ORDER.created_at`） | 乙方送出報價 → 進「待甲方付款」；甲方或乙方任一方取消 → 進「已取消」 | 待甲方付款 / 已取消 | [4.1 委託申請頁](features.md#41-委託申請頁委託人填寫)、[4.2 報價](features.md#42-報價創作者填寫) |
| 待甲方付款 | 乙方送出報價（金額、起訖日、各階段 deadline） | 甲方確認報價並完成入帳 → 進「製作中」；甲方或乙方任一方取消，或付款期限 3 天到期未入帳 → 進「已取消」 | 製作中 / 已取消 | [4.3 付款頁](features.md#43-付款頁委託人) |
| 製作中 | 平台確認入帳（**契約成立**的那一刻，契約快照全部鎖定） | 完稿定稿（見[完稿的特殊規則](#完稿stage_no5的特殊規則)）→ 進「已完成」；任一方申請終止合作並二次確認 → 進「已終止」；乙方尚未上傳完稿，整筆委託最終截稿日 +30 天後仍未了結 → 系統依終止合作結算公式強制結算 → 進「已終止」；只付訂金案件補款逾期 → 系統結算 → 進「已終止」 | 已完成 / 已終止 | [4.4 委託討論牆](features.md#44-委託討論牆) |
| 已完成 | 完稿定稿：一次付清＝委託人按「確認收稿」或 7 天窗口期滿自動完成；只付訂金＝補款入帳 | — （終態） | — | [4.5 結案畫面](features.md#45-結案畫面) |
| 已取消 | 契約成立前，甲方或乙方任一方主動取消；或付款逾期自動取消 | — （終態） | — | [4.8 取消委託燈箱](features.md#48-取消委託燈箱) |
| 已終止 | 契約成立後，任一方發起終止合作並二次確認；或乙方尚未上傳完稿、整筆委託最終截稿日 +30 天後仍未了結（系統強制結算）；或只付訂金補款逾期未補（系統結算） | — （終態） | — | [4.5 結案畫面](features.md#45-結案畫面)、[4.9 終止合作燈箱](features.md#49-終止合作燈箱) |

- **契約成立＝平台確認入帳（託管）的那一刻**。在那之前（待乙方報價、待甲方付款／等待入帳）都算「契約成立前」，用 [4.8 取消委託](features.md#48-取消委託燈箱)，免費、不需理由審核，甲方或乙方都能取消；之後只能用 [4.9 終止合作](features.md#49-終止合作燈箱)，依結算公式算錢，或等系統強制結算。
- **契約成立前不設逾期**：待乙方報價、待甲方付款（產生虛擬帳號前）都沒有系統計時，因為任一方都能隨時取消離開，沒有人會被卡住。付款期限 3 天只在產生虛擬帳號後才起算，見[二](#二計時規則)。
- **終態案件的操作全部鎖死**：已完成、已取消、已終止之後，不能再上傳、重傳、確認、補款、終止、取消。仍保留的只有：結案畫面與結算卡（唯讀）、聊天室（唯讀，可看歷史訊息、不能再傳訊）、依結算規則的稿件下載、[雙向評價](features.md#51-評價)，以及「結算後仍有應補付」時的[補付入口](#結算後的鎖帳號與補付入口)。
- `ORDER.terminated_by_id`（FK → `USER.id`，nullable）＋ `ORDER.terminated_at`：只記錄「誰、何時發起終止」。`terminated_by_id` 跟 `commissioner_id` 比對可判斷是甲方或乙方發起；`terminated_by_id` 為空值但 `status`＝已終止，代表系統結算（例：只付訂金逾期未補款，依「完稿視同已確認」結算，見[三](#三金額與結算公式)）。
- `ORDER.cancel_reason`：取消或終止合作的原因，共用同一個欄位（必填，上限 250 字，見 [4.8](features.md#48-取消委託燈箱)、[4.9](features.md#49-終止合作燈箱)），不拆欄位。

### ORDER_STAGE 的階段內狀態

`ORDER.status`＝「製作中」只代表案件還在跑，**不**代表目前在哪一階段——目前在第幾階段、該階段有沒有確認，一律查 `ORDER_STAGE`，`ORDER` 本體不存快取，避免兩處不同步。

| ORDER_STAGE 欄位 | 說明 |
| --- | --- |
| `stage_no` | 階段序號。五點分段：1 草稿、2 線稿、3 彩稿、4 精稿、5 完稿；三點分段：1 草稿、4 精稿、5 完稿（沿用五點分段的編號，不另編、不遞補）。「5＝完稿」「1＝訂金階段」的判斷對兩種分段方式都成立。 |
| `deadline` | 乙方報價時填寫，甲方確認報價時鎖入契約。**僅供參考，不會觸發任何系統動作**；只有最後一階段（`stage_no`＝5）的 deadline（＝整筆委託的最終截稿日）會被用來起算[逾期強制結算（+30 天）](#二計時規則)；補款／定稿期限不看 deadline，從乙方上傳完稿的當下起算。 |
| `submitted_at` | 乙方上傳稿件（或重傳覆蓋）的時間，記錄用途（通知、歷史紀錄）。**唯一的例外是完稿**：完稿每次上傳或重傳的時間，就是 7 天期限（`ORDER.finalize_due_at`）的起算點（見[二](#二計時規則)）；階段 1～4 的上傳不觸發任何倒數。 |
| 確認狀態 | 階段 1～4：未確認／人工確認（甲方按「確認該階段審核」）。完稿的確認方式見下一節。 |

### 完稿（stage_no＝5）的特殊規則

- **乙方上傳完稿，視同委託人已確認完稿內容**，委託人不需要逐階段審核完稿；但「定稿」（撥款、解鎖原檔、案件完成）要等下面兩種方案各自的時點才發生。
- 上傳完稿後，案件進入 **7 天窗口**（`ORDER.finalize_due_at`＝乙方最近一次上傳完稿的時間 + 7 天）。窗口內乙方**可重傳覆蓋**，每次重傳都重新計算期限。

| | 一次付清 | 只付訂金 |
| --- | --- | --- |
| 定稿時點 | 委託人按「確認收稿」（提前），或 7 天窗口期滿（自動完成） | 補款入帳 |
| 窗口期滿的後果 | 自動完成：撥清尾款、解鎖原檔 | 沒補款 → 進入 7 天等待期 → 期滿依「完稿視同已確認」結算（結果同窗口內終止） |
| 委託人拿不到什麼 | — | 補款前拿不到完稿的圖 |

- 定稿之後，完稿鎖定，不可再重傳，案件進入終態並鎖死所有操作（見[一](#一委託狀態機)）。
- 窗口期間（已上傳完稿、尚未定稿）**仍可申請終止合作**：此時完稿視同已確認階段，結算時創作者可得包含完稿費用，見[終止合作結算](#終止合作結算)。

## 二、計時規則

| 事件 | 天數 | 起算點 | 逾期後果 | 保護誰 |
| --- | --- | --- | --- | --- |
| 付款期限 | 3 天 | 產生 ATM 虛擬帳號（`PAYMENT.due_at`） | 自動取消（`ORDER.status` → 已取消），顯示[付款逾期自動取消通知頁](features.md#43-付款頁委託人) | 創作者（甲方不付款不會卡住案件） |
| 完稿定稿期限（補款期限） | 7 天 | **乙方最近一次上傳完稿的時間**（上傳當下起算 7 天，不看截稿日），記於 `ORDER.finalize_due_at`；每次完稿上傳或重傳都重算 | 一次付清：期滿自動完成。只付訂金：期滿未補款 → 進入 7 天等待期 | 創作者 |
| 補款 7 天等待期 | 7 天 | 補款期限到期（只付訂金案件） | 期滿仍未補齊 → 依「完稿視同已確認」結算（見[三](#三金額與結算公式)） | 創作者 |
| 逾期強制結算 | 30 天 | 整筆委託最終截稿日（報價時填的結束日期／最後一階段 `deadline`） | **只適用乙方尚未上傳完稿的案件**：若仍未了結（不是已完成也不是已終止），系統依[終止合作結算公式](#三金額與結算公式)強制結算（`status`→已終止，`terminated_by_id` 為空＝系統結算） | 雙方（避免案件無限期卡住） |
| 鎖帳號 | — | 任何結算（主動終止、強制結算、補款逾期）後，若仍有「委託人應補付」金額未付 | 鎖住委託人帳號，直到付清為止 | 創作者 |

- **兩條軌道互斥，以乙方是否上傳完稿切換**：乙方還沒上傳完稿走「+30 天強制結算」；乙方上傳完稿的那一刻起，改走「7 天定稿期限」（只付訂金則為 7 天補款期限＋7 天等待期）。例：乙方在截稿日 +29 天才上傳完稿，上傳當下就從 +30 軌切到 +7 軌，兩者不會同時計時。
- **重傳重置**：完稿重傳會把 `finalize_due_at` 重算；若重傳發生在只付訂金案件的 7 天等待期內，整條軌道回到「補款期限」重新開始。乙方沒上傳完稿就不產生這個期限，也不會鎖委託人帳號。
- **提前交稿**：乙方在截稿日之前上傳完稿時，從上傳當下就由 +30 軌切到 +7 軌，期限是上傳時間 + 7 天，**不需要等到截稿日**；一次付清的委託人仍可以按「確認收稿」提前定稿，不用等滿。
- **過程中沒有中途時限**：每個階段的 `deadline`、上傳與確認的時間點都只是參考，系統不會因為沒準時做什麼就自動產生後果（這取代了舊版的 auto-confirm 與創作者惡意棄單機制）。唯一的兜底是上面的「逾期強制結算」。完稿的「上傳即視同確認」是這條規則唯一的例外，且只限完稿。
- **強制結算只看委託人有沒有確認**（2026/10/15 定案，取代先前「階段 1 有上傳視為已確認」的例外）：階段 1～4 乙方有上傳、但委託人沒按確認，一律不算確認，該階段費用退還委託人，卡在階段 1 時就是雙輸（託管款全退、乙方 0）。理由：乙方可能草草上傳、委託人不滿而惡意延遲，系統不判斷誰對誰錯，雙方都有責任，這是雙輸局面；委託人另有整整 30 天可以確認或主動終止。
- 任一方自己主動發起的「終止合作」同樣遵守這個原則（撥款前終止一律雙輸）。
- 付款期限、逾期強制結算、完稿定稿期限都「站內＋email 雙管道」通知，見 [features.md 5.2](features.md#52-通知中心)。

## 三、金額與結算公式

### 階段金額拆分

契約成立後，總價與階段數已鎖進快照，本階段金額**即時計算**，不落地存值。階段數：五點分段＝5、三點分段＝3（草稿、精稿、完稿）。

- **有訂金%**（`CREATOR_PROFILE` 訂金% 30／50，於申請時鎖入 `ORDER` 快照）：
  - 第一階段（＝訂金）＝總價 × 訂金%
  - 其餘各階段 ＝ 剩餘金額 ÷ (階段數 − 1)，無條件捨去，餘數併入最後階段
- **無需先支付**：各階段 ＝ 總價 ÷ 階段數，無條件捨去，餘數併入最後階段

### 付款方案

委託人在 [4.3 付款頁](features.md#43-付款頁委託人) 選擇付款方案，兩者皆先入第三方託管：

- **一次付清**：全額入託管。撥款只發生在三個時點：第一階段確認後撥訂金、完稿定稿後撥尾款、終止合作結算；中間階段確認不另外撥款。
- **先付訂金**：只付第一階段金額入託管；差額（尾款）延到最終結算（正常完稿或中途終止合作）才一次補齊，不逐階段補款。

訂金% 設定決定付款頁顯示哪些方案卡：
- 訂金%＝30／50：顯示「先付訂金」與「一次付清」兩張卡，委託人可選。
- 訂金%＝無需先支付：**隱藏「先付訂金」卡**，只顯示「一次付清」——因為沒有訂金比例可以拆出一個「先付訂金」的金額。

### 正常完成結算

完稿定稿時一次到位：撥清剩餘託管款（尾款）＋解鎖全案無浮水印原檔＋案件完成（`ORDER.completed_at`）。定稿時點見[完稿的特殊規則](#完稿stage_no5的特殊規則)。

### 只付訂金案件的補款

- 委託人按「前往補款」匯款後按「通知已補款」：該筆入款 `PAYMENT.status` → 已通知待確認；「模擬入帳」→ 已託管。
- **補款入帳即定稿**，直接完成結案：撥清款項＋解鎖原檔，與正常完成結算相同；補款前委託人拿不到完稿的圖，也沒有「確認收稿」按鈕。
- 補款金額不存欄位，即時計算：`quote_amount` − `PAYMENT` 已託管入款 `amount` 加總。

### 終止合作結算

[4.9 終止合作燈箱](features.md#49-終止合作燈箱) 的結算試算卡用這套公式，固定三個欄位（委託人已付／創作者可得／委託人退款，退款為負數時改稱「委託人應補付」並顯示正數）。「確認」一律指**委託人按了確認**，乙方上傳但委託人沒確認的階段不算確認：

| 情境 | 創作者可得 | 委託人可得 |
| --- | --- | --- |
| 訂金%撥款前終止（卡在第一階段） | 0（雙輸：託管款全退委託人） | 全額退款；無圖可拿 |
| 訂金%撥款後終止（卡在第二階段以後） | 雙方已確認階段費用總和（全額，不對半分；第一階段就是訂金，不重複計算） | 雙方最近一次共同確認過的那一版圖（去浮水印，不是爭議中那個未確認階段的圖）＋ 爭議中未確認階段費用（全額退還）＋ 尚未開始階段費用（全額退還） |

- 不論哪個分支結案，雙方仍保留互評權利（[5.1 評價](features.md#51-評價)不限制評分資格）。
- **完稿窗口期間終止**（2026/10/15 定案）：乙方已上傳完稿、尚未定稿時，完稿視同已確認階段，終止後仍依上表「訂金%撥款後終止」計算，創作者可得包含完稿費用（一次付清＝總價全額，委託人退款 0）；只付訂金案件則「委託人已付」只有訂金，差額成為「委託人應補付」，依上面的鎖帳號規則處理。同樣是任一方可發起、立即生效、不需對方同意。
- 這套公式也適用「[逾期強制結算](#二計時規則)」情境（乙方尚未上傳完稿、整筆委託最終截稿日 +30 天後仍未了結），差別只在發起方是系統（`terminated_by_id` 為空），算法完全相同，沒有任何例外。

### 補款逾期結算（只付訂金專用）

只付訂金案件，補款 7 天等待期期滿仍未補齊，依「完稿視同已確認」結算（2026/10/17 定案，取代原本的「最後階段未完成」結算）：

- 結果與上面的「完稿窗口期間終止」完全相同：創作者可得＝總價全額；委託人已付只有訂金，差額成為「委託人應補付」。
- 委託人補付應補付金額後才能下載完稿，補付前拿不到完稿的圖。
- 結算後依下面的規則鎖帳號。
- `ORDER.status` → 已終止，`terminated_by_id` 為空值（系統結算）。
- **為什麼改**：舊規則讓創作者在完稿上傳後搶先終止，可以拿到總價全額；委託人拖滿等待期，反而比主動終止少付最後階段費用。兩條路徑結果不同，等於鼓勵雙方搶先終止或刻意拖延。改成同一套結果後，補款、主動終止、逾期三條路徑的金額一致；7 天等待期保留，作用變成鎖帳號之前的寬限期。

### 結算後的鎖帳號與補付入口

- **鎖帳號條件統一**（2026/10/15 定案）：不論哪一種結算（主動終止、逾期強制結算、補款逾期），只要結算後仍有「委託人應補付」未付，一律鎖住委託人帳號，直到付清為止。
- **鎖帳號只擋「送出新委託」**（2026/10/17 定案）：被鎖的委託人仍可登入、瀏覽、使用補付入口；不論是以委託人還是創作者身分，手上的進行中案件都照常進行，避免連累沒有欠款的另一方。後端只在 `POST /orders` 檢查 `USER.account_status`。
- 案件本身已是終態，所有操作鎖死；只保留一個「補付應補付金額」入口，顯示在該案的結案畫面：委託人看到應補付金額與 ATM 匯款資訊，匯款後按「通知已補付」，「模擬入帳」後帳號解鎖。案件 `status` 維持已終止，不回到製作中。
- 補付入款以一筆新的 `PAYMENT` 紀錄表示（用途為結算後補付）；欄位細節以 FigJam 為準，見 [data-model.md 第 6 節](data-model.md#6-圖上目前已知的問題)。

## 四、Payment 狀態

`PAYMENT.status` 列舉與觸發動作：

| 狀態 | 觸發動作 |
| --- | --- |
| 待託管 | 產生 ATM 虛擬帳號（`PAYMENT.virtual_account_no`／`bank_code`／`due_at`），等待委託人匯款 |
| 已通知待確認 | 委託人按「通知已付款」／「通知已補款」／「通知已補付」 |
| 已託管 | 平台確認入帳（demo：按「模擬入帳」），寫入 `paid_at` |
| 已撥款 | 依[三](#三金額與結算公式)公式撥給創作者（訂金撥款／尾款撥款） |
| 已退款 | 已取消、終止合作雙輸，或終止合作結算中「全額退還」部分 |
| 已逾期 | 付款期限（3 天）到期仍為「待託管」 |
| 已取消 | 已逾期後案件自動取消，該筆託管入款作廢 |

- `PAYMENT` 不串真實金流，只做狀態紀錄用途；不做 6% 平台抽成計算。
- **金額一致才成立**：假設第三方金流以「匯款金額與應付金額完全一致」為成立條件，金額不符，該筆入款不成立。這個機制 Demo 無法呈現，只記在 spec；因此 `PAYMENT.status` 不需要「部分付款」狀態，付款、補款、補付金額都是即時算出的單一數字。

## 五、契約快照與同意

[4.6 契約與授權](features.md#46-契約與授權) 定義了契約規則本身（服務條款、授權層級判準等），這裡只列哪些欄位在什麼時間點鎖定：

| 欄位 | 鎖定時間點 |
| --- | --- |
| `ORDER.item_title_snapshot`（項目標題） | 甲方**送出委託申請時**從 `COMMISSION_ITEM` 複製鎖定 |
| `ORDER.item_description_snapshot`（項目說明）、`ORDER_ITEM_SNAPSHOT_IMAGE`（項目範例圖片） | 甲方**送出委託申請時**從 `COMMISSION_ITEM`／`COMMISSION_ITEM_IMAGE` 複製鎖定（2026/10/17 定案）。案件畫面上的項目資訊一律讀快照，所以創作者之後修改或刪除該項目都不影響案件 |
| `ORDER.deposit_percent_snapshot`（訂金比例） | 送出委託申請時，從 `CREATOR_PROFILE` 複製鎖定 |
| `ORDER.stage_plan_snapshot`（分段方案） | 甲方**送出委託申請時**就從 `COMMISSION_ITEM.stage_plan_pref` 複製鎖定，避免乙方在報價前改項目分段 |
| `ORDER.revision_count_snapshot`（修改次數） | 送出委託申請時，從 `CREATOR_PROFILE.revision_count` 複製鎖定 |
| 授權層級（個人／商業） | 送出委託申請時選定，成立後不可事後擴大授權 |
| 委託報價金額、起訖日、各階段 `deadline` | 乙方報價時填寫，甲方確認報價時鎖定 |
| `ORDER.creator_agreed_at` | 乙方送出報價、同意服務條款時記錄（此時價格與期限已存在） |
| `ORDER.commissioner_agreed_at` | 甲方**在付款頁看過報價、按「確認送出」時**記錄（2026/10/15 起，不再記在送出申請時，因為申請時還沒有價格）；申請頁的同意勾選只是送出申請的前置條件，不另存時間，`ORDER.created_at` 即為送出申請時間 |
| 其餘契約快照（表單填寫內容、付款方式等） | 平台確認入帳（契約成立）時全部鎖定，成立後平台只認最初的契約 |

契約成立後，金額、規格、授權範圍若雙方私下談出異動，不進平台金流、平台不提供重新簽約（見 [4.6](features.md#46-契約與授權)）。
