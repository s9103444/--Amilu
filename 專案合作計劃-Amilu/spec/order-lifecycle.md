## 一、委託狀態機

### ORDER.status

| 狀態 | 進入條件 | 誰能讓它離開這個狀態 | 離開後去哪裡 | 對應畫面 |
| --- | --- | --- | --- | --- |
| 待乙方報價 | 甲方按「我要委託」送出申請（`ORDER.created_at`） | 乙方送出報價 → 進「待付款」；甲方或乙方任一方取消 → 進「已取消」 | 待付款 / 已取消 | [4.1 委託申請頁](features.md#41-委託申請頁委託人填寫)、[4.2 報價](features.md#42-報價創作者填寫) |
| 待付款 | 乙方送出報價（金額、起訖日、各階段 deadline） | 甲方確認報價並完成入帳 → 進「進行中」；甲方取消，或付款期限 3 天到期未入帳 → 進「已取消」 | 進行中 / 已取消 | [4.3 付款頁](features.md#43-付款頁委託人) |
| 進行中 | 平台確認入帳（**契約成立**的那一刻，契約快照全部鎖定） | 最後階段確認完成 → 進「已完成」；任一方申請終止合作並二次確認 → 進「已終止」；創作者逾期未交稿（惡意棄單） → 進「已終止」 | 已完成 / 已終止 | [4.4 委託討論牆](features.md#44-委託討論牆) |
| 已完成 | 最後階段經人工確認、auto-confirm，或只付訂金者補款入帳（視同確認最後階段） | — （終態） | — | [4.5 結案畫面](features.md#45-結案畫面) |
| 已取消 | 契約成立前，甲方或乙方任一方主動取消；或付款逾期自動取消 | — （終態） | — | [4.8 取消委託燈箱](features.md#48-取消委託燈箱) |
| 已終止 | 契約成立後，任一方發起終止合作並二次確認；或創作者惡意棄單；或只付訂金逾期未補款（系統結算） | — （終態） | — | [4.5 結案畫面](features.md#45-結案畫面)、[4.9 終止合作燈箱](features.md#49-終止合作燈箱) |

- **契約成立＝平台確認入帳（託管）的那一刻**。在那之前（待乙方報價、待付款／等待入帳）都算「契約成立前」，用 [4.8 取消委託](features.md#48-取消委託燈箱)，免費、不需理由審核；之後只能用 [4.9 終止合作](features.md#49-終止合作燈箱)，依結算公式算錢。
- `ORDER.terminated_by_id`（FK → `USER.id`，nullable）＋ `ORDER.terminated_at`：只記錄「誰、何時發起終止」。`terminated_by_id` 跟 `commissioner_id` 比對可判斷是甲方或乙方發起；`terminated_by_id` 為空值但 `status`＝已終止，代表系統結算（例：只付訂金逾期未補款，以「最後階段未完成」結算，見[三](#三金額與結算公式)）。
- `ORDER.cancel_reason`：已取消時的取消原因（必填，上限 250 字，見 [4.8](features.md#48-取消委託燈箱)）。

### ORDER_STAGE 的階段內狀態

`ORDER.status`＝「進行中」只代表案件還在跑，**不**代表目前在哪一階段——目前在第幾階段、該階段有沒有確認，一律查 `ORDER_STAGE`，`ORDER` 本體不存快取，避免兩處不同步。

| ORDER_STAGE 欄位 | 說明 |
| --- | --- |
| `stage_no` | 階段序號。五點分段：1～5；單段：只有 5（5＝完稿），讓「完稿＝5」的判斷邏輯對兩種分段方式都成立。 |
| `deadline` | 乙方報價時填寫，甲方確認報價時鎖入契約。 |
| `submitted_at` | 乙方上傳稿件（或重傳覆蓋）的時間，auto-confirm 倒數從最近一次上傳重新起算。 |
| 確認狀態 | 未確認／人工確認（甲方按「確認該階段審核」）／auto-confirm（系統代為確認）。 |

## 二、計時規則

| 事件 | 天數 | 起算點 | 逾期後果 | 保護誰 |
| --- | --- | --- | --- | --- |
| 付款期限 | 3 天 | 產生 ATM 虛擬帳號（`PAYMENT.due_at`） | 自動取消（`ORDER.status` → 已取消），顯示[付款逾期自動取消通知頁](features.md#43-付款頁委託人) | 創作者（甲方不付款不會卡住案件） |
| auto-confirm | 5 天 | 乙方上傳該階段稿件（`ORDER_STAGE.submitted_at`） | 系統代為確認該階段，案件繼續進下一階段；討論牆確認按鈕改顯示「系統已於 X 代為確認」 | 創作者（甲方沉默不會卡住進度） |
| 創作者惡意棄單 | 5 天 | 該階段 `deadline` | 創作者逾期未上傳任何稿件：只留訂金、封鎖創作者帳戶，案件以「已終止」結案（`terminated_by_id` 為空＝系統結算） | 委託人 |
| 補款期限 | 自創作者上傳最後階段起算（`ORDER_STAGE.submitted_at`，`stage_no`＝5） | `ORDER.topup_due_at` | 到期後進入 7 天等待期 | — |
| 補款 7 天等待期 | 7 天 | 補款期限到期 | 期滿仍未補齊 → 以「最後階段未完成」結算（見[三](#三金額與結算公式)） | 創作者 |
| 鎖帳號 | — | 「最後階段未完成」結算後，若仍有「委託人應補付」金額未付 | 鎖住委託人帳號，直到付清為止 | 創作者 |

- **惡意棄單只適用於創作者**。委託人側沒有對稱的「惡意棄單」狀態：委託人在確認階段沉默由 auto-confirm 保護創作者、讓案件繼續；只有在「只付訂金」案件的補款逾期走完 7 天等待期、結算後仍欠款，才會鎖委託人帳號——這是**結算後的欠款鎖帳**，不是棄單判定。
- 付款期限、auto-confirm、惡意棄單三種計時都「站內＋email 雙管道」通知，見 [features.md 5.2](features.md#52-通知中心)。

## 三、金額與結算公式

### 階段金額拆分

契約成立後，總價與階段數已鎖進快照，本階段金額**即時計算**，不落地存值：

- **有訂金%**（`CREATOR_PROFILE` 訂金% 30／50，於申請時鎖入 `ORDER` 快照）：
  - 第一階段（＝訂金）＝總價 × 訂金%
  - 其餘各階段 ＝ 剩餘金額 ÷ (階段數 − 1)，無條件捨去，餘數併入最後階段
- **無需先支付**：各階段 ＝ 總價 ÷ 階段數，無條件捨去，餘數併入最後階段
- 單段委託：階段數＝1，全額即為該階段金額。

### 付款方案

委託人在 [4.3 付款頁](features.md#43-付款頁委託人) 選擇付款方案，兩者皆先入第三方託管：

- **一次付清**：全額入託管，後續依上面公式逐階段撥款。
- **先付訂金**：只付第一階段金額入託管；差額（尾款）延到最終結算（正常完稿或中途終止合作）才一次補齊，不逐階段補款。

訂金% 設定決定付款頁顯示哪些方案卡：
- 訂金%＝30／50：顯示「先付訂金」與「一次付清」兩張卡，委託人可選。
- 訂金%＝無需先支付：**隱藏「先付訂金」卡**，只顯示「一次付清」——因為沒有訂金比例可以拆出一個「先付訂金」的金額。

### 正常完成結算

最後階段經人工確認或 auto-confirm：一次到位——撥清剩餘託管款（尾款）＋解鎖全案無浮水印原檔＋案件完成（`ORDER.completed_at`）。

### 只付訂金案件的補款

- 委託人按「前往補款」匯款後按「通知已補款」：該筆入款 `PAYMENT.status` → 已通知待確認；「模擬入帳」→ 已託管。
- **補款入帳即視同確認最後階段**，直接完成結案：撥清款項＋解鎖原檔，與正常完成結算相同；最後階段不走 auto-confirm（必須補款才能確認）。
- 補款金額不存欄位，即時計算：`quote_amount` − `PAYMENT` 已託管入款 `amount` 加總。

### 終止合作結算

[4.9 終止合作燈箱](features.md#49-終止合作燈箱) 的結算試算卡用這套公式，固定三個欄位（委託人已付／創作者可得／委託人退款，退款為負數時改稱「委託人應補付」並顯示正數）：

| 情境 | 創作者可得 | 委託人可得 |
| --- | --- | --- |
| 訂金%撥款前終止（卡在第一階段或單段交易） | 0（雙輸：託管款全退委託人） | 全額退款；無圖可拿 |
| 訂金%撥款後終止（多段交易，卡在第二階段以後） | 訂金% ＋ 雙方已確認階段費用（全額，不對半分） | 雙方最近一次共同確認過的那一版圖（去浮水印，不是爭議中那個未確認階段的圖）＋ 爭議中未確認階段費用（全額退還）＋ 尚未開始階段費用（全額退還） |

- 不論哪個分支結案，雙方仍保留互評權利（[5.1 評價](features.md#51-評價)不限制評分資格）。

### 「最後階段未完成」結算（逾期未補款專用）

只付訂金案件，補款 7 天等待期期滿仍未補齊：

- 最後階段費用退還給委託人。
- 創作者拿已確認階段（不含最後階段）的費用。
- 委託人只拿前一個已確認階段的無浮水印圖（**拿不到最後階段的圖**）。
- 結算後若「委託人應補付」（已確認階段費用總和超過已付訂金的部分）仍未付，鎖委託人帳號直到付清。
- `ORDER.status` → 已終止，`terminated_by_id` 為空值（系統結算）。

## 四、Payment 狀態

`PAYMENT.status` 列舉與觸發動作：

| 狀態 | 觸發動作 |
| --- | --- |
| 待託管 | 產生 ATM 虛擬帳號（`PAYMENT.virtual_account_no`／`bank_code`／`due_at`），等待委託人匯款 |
| 已通知待確認 | 委託人按「通知已付款」／「通知已補款」 |
| 已託管 | 平台確認入帳（demo：按「模擬入帳」），寫入 `paid_at` |
| 已撥款 | 依[三](#三金額與結算公式)公式撥給創作者（訂金撥款／尾款撥款） |
| 已退款 | 已取消、終止合作雙輸，或終止合作結算中「全額退還」部分 |
| 已逾期 | 付款期限（3 天）到期仍為「待託管」 |
| 已取消 | 已逾期後案件自動取消，該筆託管入款作廢 |

`PAYMENT` 不串真實金流，只做狀態紀錄用途；不做 6% 平台抽成計算。

## 五、契約快照與同意

[4.6 契約與授權](features.md#46-契約與授權) 定義了契約規則本身（服務條款、授權層級判準等），這裡只列哪些欄位在什麼時間點鎖定：

| 欄位 | 鎖定時間點 |
| --- | --- |
| `ORDER.stage_plan_snapshot`（分段方案） | 甲方**送出委託申請時**就從 `COMMISSION_ITEM.stage_plan_pref` 複製鎖定，避免乙方在報價前改項目分段 |
| `ORDER.revision_count_snapshot`（修改次數） | 送出委託申請時，從 `CREATOR_PROFILE.revision_count` 複製鎖定 |
| 授權層級（個人／商業） | 送出委託申請時選定，成立後不可事後擴大授權 |
| 委託報價金額、起訖日、各階段 `deadline` | 乙方報價時填寫，甲方確認報價時鎖定 |
| `ORDER.commissioner_agreed_at` | 甲方送出委託申請、同意服務條款時記錄 |
| `ORDER.creator_agreed_at` | 乙方送出報價、同意服務條款時記錄 |
| 其餘契約快照（表單填寫內容、付款方式等） | 平台確認入帳（契約成立）時全部鎖定，成立後平台只認最初的契約 |

契約成立後，金額、規格、授權範圍若雙方私下談出異動，不進平台金流、平台不提供重新簽約（見 [4.6](features.md#46-契約與授權)）。
